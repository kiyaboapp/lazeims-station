# LAZEIMS Offline Station — Complete Implementation Plan

**Status:** Implementation plan; no application-code changes are authorized by this document alone.  
**Architecture retained:** FastAPI + SQLite LAN server with fully local HTML/CSS/JS.  
**Primary users:** non-technical Chief IT / Station Exam Admin and several Data Enterers on one LAN.  
**Source requirements:** `LAZEIMS_Implementation_Guide.md` Part 6, current FastAPI Central/Station contracts, and the operational requirement that ordinary users never manage Python, pip, virtual environments, or shell commands.

## 1. Product outcome

A Chief IT must be able to prepare and operate a Station as follows:

1. On a new Windows or Linux computer, run one guided setup by double-clicking a launcher.
2. See a clear, colorful terminal that explains each stage in non-technical language.
3. Import a small, signed Station exam package generated by Central.
4. Start the same persistent Station on every later day by double-clicking one shortcut.
5. Let multiple Data Enterers use browsers over the LAN with no installation on their devices and no internet during entry.
6. Import later package versions without creating another environment or another accidental SQLite database.
7. Synchronize directly or by controlled removable-media exchange.
8. Back up, restore, upgrade, and reconcile without losing marks, attendance, incidents, audit records, or pending events.

The Station must never create exams or process results.

## 2. Non-negotiable decisions

### 2.1 Separate the three lifecycles

The existing complete-bundle implementation mixes runtime setup, application source, exam data, and SQLite storage in each extracted folder. Replace that operational model with three separately versioned lifecycles:

1. **Host setup** — performed once on a computer.
2. **Station application release** — upgraded occasionally when LAZEIMS Station code or dependencies change.
3. **Exam package** — imported whenever Central issues or revises the scope/configuration for a station and exam.

Exam-package import must never install Python, create an environment, or select a new arbitrary data folder.

### 2.2 Environment policy

- A dependency environment is **never created per package**.
- The first host setup creates the environment required by the installed Station release.
- Environments are keyed by the SHA-256 hash of `requirements.lock`, for example `envs/sha256-abcd.../`.
- Importing multiple package versions with the same Station application creates no environment and performs no dependency installation.
- A new environment is created only when an application upgrade has a different dependency-lock hash. The previous environment is retained temporarily for rollback and later pruned.
- The launcher never says “venv”, “pip”, or “Python” in normal operator output. Detailed diagnostics may record the exact runtime and dependency versions.

This preserves isolation and rollback without exposing technical setup or recreating environments for exams.

### 2.3 Persistent data policy

Use stable OS data paths, never the extracted download directory:

```text
Windows: %LOCALAPPDATA%\LAZEIMS\
Linux:   ${XDG_DATA_HOME:-~/.local/share}/lazeims/

LAZEIMS/
├── install.json                    # installation ID and current release
├── launcher/                       # stable launcher files
├── app/
│   ├── releases/<software-version>/
│   └── current.json                # atomic current-release pointer
├── envs/<requirements-lock-sha256>/
├── stations/
│   └── <station-code>/
│       └── exams/<exam-id>/
│           ├── station.sqlite3
│           ├── .session-secret
│           ├── imports/
│           │   ├── pending/
│           │   ├── imported/
│           │   └── failed/
│           ├── packages/
│           ├── backups/
│           ├── exports/
│           └── logs/
└── logs/                            # setup and launcher logs
```

Rules:

- Multiple versions for the same station and exam import into the same SQLite database.
- A new exam receives a separate SQLite database so natural keys and archived data cannot collide.
- Old exams remain available read-only for the retention/dispute period.
- Only one active Station process uses port 8080 at a time. If several station/exam datasets exist, the local admin selects the active one before startup.
- The same Windows account should operate the Station. Backup/export provides controlled transfer to a replacement account or computer.

### 2.4 Artifact policy

Produce immutable, signed artifacts in CI/release tooling. Central should serve stored artifacts; it should not assemble a runtime from live source on every package download.

#### A. Lean Station Setup Kit

Suggested name:

```text
LAZEIMS-Station-Setup-Online-<version>.zip
```

Contents:

- `Setup LAZEIMS Station.bat`
- `launcher/setup.ps1`
- release manifest and public verification key
- Station source/static assets or a signed application-release archive
- pinned official Python download metadata
- `requirements.lock`
- exact SHA-256 hashes

Behavior: if the managed runtime is absent, download only the pinned official installer and locked dependencies, verify them, and install per-user. Internet is required only for this first setup or a later application upgrade that changes dependencies.

#### B. Full Offline Station Setup Kit

Suggested name:

```text
LAZEIMS-Station-Setup-Offline-<version>.zip
```

It contains everything in the lean kit plus:

- the pinned official Python installer for the target OS/architecture;
- its expected SHA-256 and Authenticode signer information;
- the complete hash-locked wheelhouse.

This artifact will naturally be much larger, but it is transferred once per host—not once per exam package. It may be reused from a controlled USB drive for many station computers.

#### C. Station Application Update

Suggested name:

```text
LAZEIMS-Station-Update-<version>.lazeims-update.zip
```

Contents: signed Station source/static assets, `lazeims_common`, schema/software compatibility metadata, `requirements.lock`, and an offline wheelhouse only when needed. Updates install into a staged release directory, verify, back up data, migrate, health-check, and atomically switch `current.json`.

#### D. Station Exam Package

Suggested name:

```text
<station-code>-<exam-code>-P<package-version>.lazeims-package.zip
```

This is the normal small operational download. It is a ZIP, not bare JSON. It contains:

```text
manifest.json
seed.json
credentials.json                 # credential hashes and local scopes
machine-credential.json          # package-bound plaintext secret; sensitive
SHA256SUMS
SIGNATURE.ed25519
README.txt
```

It contains only assigned schools, candidates, registrations, subjects, applicable papers/questions, credential hashes/scopes, Central URL, compatibility versions, and a package-bound machine credential. It contains no Station runtime, no processing credential, and no unrelated data.

The package is a sensitive artifact. After successful import, the plaintext machine credential is protected locally and the source package is moved to a restricted archive or securely removed according to retention policy.

## 3. First-time setup workflow

### 3.1 Central preparation

Replace the fragmented Station Console actions with a single **Prepare Offline Station** wizard:

1. **Station identity** — code, display name, geography, manager.
2. **Collection scope** — enrolled schools, registered subjects with candidate counts, and applicable papers.
3. **Entry method** — set the selected `(exam, school, subject, paper)` combinations to **Offline Station**. Never expose the internal word “writer”. Show conflicts with Online/Excel and require an explicit reassignment confirmation.
4. **Station team** — choose existing exam-scoped Data Enterers and assign school/subject scope. Issue initials + PIN. Create the Station Exam Admin username + password.
5. **Readiness check** — verify scope is enrolled/configured, credentials exist, Central public URL is configured, package signing is available, and no collection-channel combinations are missing.
6. **Generate package** — create the package and package-bound machine key in one transaction; Central stores only the machine-key hash.
7. **Handover** — download the exam package and a printable credential sheet. Plaintext human credentials are shown once. Do not require email or SMS.
8. **Computer choice** — show two unambiguous buttons:
   - `First time on this computer` → Lean Setup Kit / Full Offline Setup Kit instructions.
   - `LAZEIMS Station is already installed` → exam package only.

Generating a package must create or validate the corresponding Station collection-channel assignments. It must not silently overwrite conflicting assignments.

### 3.2 Chief IT setup

The Chief IT performs only these actions:

1. Extract the setup ZIP.
2. Double-click `Setup LAZEIMS Station.bat` (Windows) or `Setup LAZEIMS Station` (Linux).
3. Watch the guided progress screen.
4. When prompted in the automatically opened local setup page, select the `.lazeims-package.zip` file.
5. Sign in with the issued full admin username and password.
6. Confirm the readiness page and share the displayed LAN URL/QR code with Data Enterers.

No command entry, PATH configuration, dependency installation, or manual environment activation is allowed.

### 3.3 First-package bootstrap security

Before a Station identity exists:

- the setup/import route is available only from `127.0.0.1`/`::1`;
- it accepts only a valid signed package;
- it closes permanently after the first station/exam is adopted;
- later package imports require an authenticated Station Exam Admin;
- a package for another station is routed to a separate station identity only through an explicit local-admin action, never silently.

## 4. Polished launcher and terminal UX

### 4.1 Implementation approach

- Windows double-click entry: a tiny `Start LAZEIMS Station.bat` shim invokes a signed/hash-verified local PowerShell launcher using built-in Windows PowerShell. No custom LAZEIMS `.exe` is produced.
- Linux entry: `start.sh` invokes the equivalent launcher logic.
- PowerShell uses `Write-Host -ForegroundColor`; modern ANSI is optional, not required.
- Every screen also works without color and with ASCII fallback glyphs.
- Operator output is concise and non-technical. Full commands, stack traces, versions, and subprocess output go to a timestamped diagnostic log.
- Secrets, PINs, passwords, cookies, package machine keys, and request authorization headers are always redacted.

### 4.2 Color and status language

| State | Color | Prefix | Meaning |
|---|---|---|---|
| Header/info | Cyan | `●` | identity, version, URLs |
| In progress | Blue | `→` | current step |
| Success | Green | `✓` | completed safely |
| Warning | Yellow | `!` | usable but attention needed |
| Failure | Red | `✗` | cannot safely continue |
| Detail | Dark gray | indented | optional explanatory detail |

Do not use raw technical phrases such as “creating venv”, “pip install”, “module import”, or “Uvicorn exception” in normal output. Use “Preparing Station engine”, “Installing required components”, “Checking Station files”, and “Starting the LAN service”.

### 4.5 Required launcher stages

#### First setup

1. Switch to the launcher directory.
2. Create/open the timestamped plain-text log.
3. Verify setup manifest, every file hash, and release signature before execution.
4. Detect OS, architecture, user-writable installation path, available disk, and whether execution is from inside a ZIP.
5. Locate a real supported Python, ignoring Windows Store aliases/stubs.
6. If absent or incompatible:
   - full offline: verify SHA-256 and Authenticode signer of the bundled official installer, then install per-user;
   - lean: test the pinned official download endpoint, download, verify, and install per-user;
   - if neither is possible: stop with an actionable message directing the operator to the Full Offline Setup Kit.
7. Install the Station application into a versioned release directory.
8. Create/reuse the environment for the exact lock hash and install with `--require-hashes`; never use unconstrained package names.
9. Create stable data/log directories and installation identity.
10. Run application self-test and SQLite capability checks.
11. Check port and LAN/firewall state.
12. Start the service, poll `/health` until ready, then open the browser.
13. Create desktop/Start Menu shortcut only after health succeeds.

#### Later launch

1. Verify stable launcher/current-release metadata.
2. Resolve active station/exam data path.
3. Verify the matching dependency environment exists; do not contact the internet.
4. Take a pre-migration backup if the schema must change.
5. Apply safe migrations and verify SQLite integrity.
6. Process pending signed imports transactionally.
7. Check port 8080.
8. Detect usable private LAN IPv4 addresses.
9. Start Station, wait for health, display/open URLs and render the QR code.

### 4.6 Port behavior

- If port 8080 already responds with the same installation/station health identity, report `Station is already running`, display the URLs, and open the browser. Do not start a second process.
- If another application owns the port, do not kill it. Show a red `PORT-001` message, the application/process details when safely available, and the diagnostic log path.
- A temporary alternate port may be offered only to an authenticated/authorized local admin and must be clearly displayed. Default operational documentation remains port 8080.

### 4.7 LAN and firewall behavior

- Exclude loopback, APIPA (`169.254.*`), disconnected, and obvious virtual/VPN adapters when choosing the primary LAN address.
- If several valid private addresses exist, show all and mark the recommended one.
- On Windows, limit any firewall rule to TCP 8080 on the Private profile and label it `LAZEIMS Offline Station`.
- Setup may request one UAC approval to create the firewall rule. If approval is unavailable, local use may continue but show a yellow warning explaining that other devices may be blocked and how authorized IT can allow Private-network access.
- Never open the port on the Public firewall profile automatically.

### 4.8 Logging and errors

Keep separate rotating logs:

- `setup-YYYYMMDD-HHMMSS.log`
- `launcher-YYYYMMDD-HHMMSS.log`
- `station-YYYYMMDD.log`
- `sync-YYYYMMDD.log`
- `audit` remains inside SQLite and is not replaced by text logs.

Terminal messages contain a stable support code:

- `SETUP-FILE-001` — setup file missing/corrupt
- `SETUP-ENGINE-001` — managed runtime could not be prepared
- `SETUP-NET-001` — lean setup cannot reach pinned source
- `PKG-SIGN-001` — package authenticity failed
- `PKG-TARGET-001` — wrong station/exam
- `PKG-UPGRADE-001` — newer Station software required
- `DB-INTEGRITY-001` — SQLite integrity failure
- `DB-MIGRATE-001` — safe migration failed and rollback was applied
- `PORT-001` — port occupied by another application
- `LAN-001` — no usable LAN address
- `START-HEALTH-001` — process started but health check failed

On failure:

1. stop safely;
2. restore the prior release/database when applicable;
3. show a plain-language cause and exact next action;
4. show the log path and support code;
5. keep the window open until the operator presses Enter;
6. never present a raw traceback as the only explanation.

## 5. Package and database lifecycle

### 5.1 Package contract

Use the canonical `station-package/v1` contract in `lazeims_common` with:

- `package_id`, `package_version`, `supersedes_package_id`;
- `station_code`, `exam_id`, human exam name/code;
- `rules_version`, `schema_min_version`, `software_min_version`;
- `configuration_hash` and full file hashes;
- exact scoped schools/subjects/applicable papers;
- issued/expiry/revocation metadata;
- Central base URL;
- package-bound machine credential identifier;
- Ed25519 signature metadata.

Use asymmetric signing. The current HMAC signature cannot be independently verified by a Station without distributing the signing secret. Central keeps the Ed25519 private key; Station releases contain only the public verification key.

### 5.2 Package-bound machine authentication

- Generate a random machine secret for each package.
- Store only its Argon2id hash and credential ID in Central.
- Carry the plaintext once inside the sensitive signed package.
- Protect it locally after import using OS-protected storage where available (Windows DPAPI without an external package); use strict file permissions and a local installation key on Linux.
- Add `package_id` to every outbox event.
- Retain machine credentials for packages that still have pending events.
- Group direct sync by package and authenticate each batch with the matching package credential.
- Revoking one package does not expose or revoke unrelated packages.
- Remove the current need for an operator to paste a Station key into the local UI.

### 5.3 Transactional import

Import sequence:

1. Read ZIP with bounded total/uncompressed size and reject path traversal.
2. Verify release/public-key trust, signature, and every file hash.
3. Validate contract/software/rules/schema compatibility.
4. Route to the correct `<station-code>/<exam-id>` data directory.
5. Take and verify an online SQLite backup when updating an existing dataset.
6. Preflight scope/configuration changes and reject unsafe mutation of entered/finalized data.
7. Import manifest, scope, seed, credentials, and machine credential in one SQLite transaction.
8. Record immutable package/import audit data.
9. Commit, run integrity/readiness checks, then mark the package active.
10. Move the source artifact to `imported/`; quarantine failures under `failed/` with a human-readable reason.

Do not use destructive `INSERT OR REPLACE` against configuration referenced by marks. Use stable natural keys plus explicit `INSERT ... ON CONFLICT DO UPDATE` with compatibility checks. Package updates must never change question identity/maxima or remove registered scope after marks exist unless Central issues an explicit correction revision that the local admin acknowledges and the system can migrate safely.

### 5.4 Local package tables

Extend SQLite with at least:

- `packages`: status (`IMPORTED`, `ACTIVE`, `SUPERSEDED`, `REVOKED`, `FAILED`), versions, hashes, timestamps;
- `package_scopes`: package-to-school/subject/paper ownership;
- `machine_credentials`: encrypted/protected package credential and status;
- `package_imports`: source file, outcome, error code, actor, backup reference;
- `user_scopes`: actual DE school/subject restrictions;
- `local_sessions`: revocable sessions and expiry;
- `login_attempts`: rate limit/lockout state;
- `browser_submit_receipts`: client idempotency responses;
- `sync_attempts`, `rejected_events`, and `reconciliations` where missing/incomplete;
- `outbox_events.package_id` and payload hash.

Credential import must upsert by stable assignment identity and apply explicit active/revoked state; it must not duplicate users on each package version.

## 6. Local authentication and authorization

### 6.1 Data Enterer

- Login with initials + short PIN.
- Normalize initials consistently but do not reveal whether initials or PIN was wrong.
- Resolve role and all allowed school/subject scopes from SQLite.
- `/api/scopes`, roster, attendance, incidents, marks, locks, and finalize must enforce those scopes server-side.

### 6.2 Station Exam Admin

- Login with full username + password.
- Add a dedicated `username` field; never store the username in `initials` or truncate it to ten characters.
- Admin-only operations: package import, sync authorization/run, portable exchange, backup/restore, application update, active-exam selection, user/lock management, diagnostics, and closeout.

### 6.3 Session protection

- Argon2id hashes only; plaintext shown once centrally.
- Server-side revocable session record with an opaque HttpOnly, SameSite cookie.
- CSRF token on every state-changing browser request.
- Login throttling and timed lockout per account/source.
- Regenerate session on authentication and delete it on logout/expiry.
- Do not trust role/scope claims from the browser or solely from a signed client cookie.
- Do not log credentials or machine keys.

## 7. Local Station browser experience

### 7.1 Setup/Admin dashboard

Provide a clear local admin dashboard with:

- Station code, exam, package version, software version, LAN URL and QR;
- package-import drop zone/file picker and import history;
- candidate/scope counts and configuration-readiness status;
- Data Enterer login readiness;
- current locks and audited force-release;
- pending/accepted/rejected sync counts with actionable rejection details;
- direct sync and portable exchange controls;
- automatic backup state, manual verified backup export, and restore workflow;
- reconciliation state per finalized scope;
- diagnostics download with secrets removed;
- application-update import/status.

### 7.2 Data entry

Retain the authoritative flow:

```text
Login → assigned school/subject/paper → acquire lock → transcribe ISAL attendance
→ raise incidents where evidence/scripts disagree → enter complete marks
→ local completion sweep → finalize → outbox/sync
```

Required behavior:

- no blank mark for a present candidate;
- explicit zero is visually distinct and valid;
- absent candidates have zero mark rows;
- attendance is required before marks;
- unresolved incidents block finalize;
- total/item mode comes from exam configuration;
- complete student-paper replacement is atomic;
- IndexedDB draft + browser outbox survives refresh/LAN interruption;
- SQLite write and outbox event share one transaction;
- draft clears only after idempotent server acknowledgement;
- keyboard-efficient marks grid and accessible live status;
- multiple browsers cannot acquire the same scope concurrently.

## 8. Sync, portable exchange, and reconciliation

### 8.1 Direct synchronization

- Only an authenticated Station Exam Admin authorizes manual/automatic sync.
- Do not automatically enable sync merely because a scope was finalized.
- Auto-sync authorization is recorded and expires with the active package/exam.
- Oldest pending events are sent in bounded batches, grouped by package credential.
- Per-event accepted/duplicate/rejected outcomes update local state individually.
- Network failure returns unacknowledged `SENDING` events to `PENDING` with exponential backoff and jitter.
- Entry never waits for Central.
- Central rechecks phase, package status, package scope, collection channel, natural keys, and canonical validation.

### 8.2 Portable exchange

Complete an admin UI for signed, encrypted, recipient-bound event/acknowledgement envelopes. It must reuse the same Central event-processing service as HTTPS, reject alteration/replay/wrong recipient/expiry, and never copy SQLite as a sync method.

### 8.3 Reconciliation and closeout

For every finalized scope, compute deterministic canonical counts and hashes for attendance, incidents, and marks. Closeout requires:

- pending events = 0;
- rejected events = 0;
- all intended package scopes finalized;
- Central digest matches local digest;
- no unresolved incident.

After closeout, make that exam dataset read-only and retain it with verified backups for the dispute period.

## 9. Backup, restore, upgrades, and migration

### 9.1 Automatic backup policy

Use SQLite online backup API only. Create and verify snapshots:

- before every schema/application upgrade;
- before an existing-exam package changes configuration/scope;
- at first committed entry of each day;
- on admin request;
- before restore.

Keep a configurable rolling local set and support an admin-exported backup to removable media. A backup is successful only after `PRAGMA integrity_check` returns `ok`.

### 9.2 Restore policy

Restore runs only while entry is paused and requires admin authentication plus confirmation. It first snapshots the current database, verifies the selected backup, restores through SQLite backup API, restarts, and clearly marks reconciliation required because restored data may be behind Central.

### 9.3 Application upgrade

1. Import/download signed update.
2. Verify signature/hashes and compatibility.
3. Stage under `app/releases/<version>`.
4. Reuse existing environment if lock hash matches; otherwise create one environment for the new lock hash.
5. Back up every affected active database.
6. Run migrations and self-tests.
7. Start a temporary health check.
8. Atomically switch current release.
9. On failure, restore prior pointer/database and retain detailed diagnostics.

Never overwrite the only known-good application release or environment.

### 9.4 Migration from current complete bundles

Provide a one-time migration path:

- detect `./station_data/station.sqlite3` beside an old bundle launcher;
- stop if both legacy and target databases contain divergent entries;
- take and verify backups of both;
- move/import legacy data into the canonical station/exam directory;
- preserve session secrets only when safe; otherwise invalidate sessions;
- preserve package rows, marks, attendance, incidents, audit, outbox status, and sync configuration;
- record migration source and hashes;
- never delete the old folder automatically; rename it as migrated after verification.

Existing v1 machine-key and package authentication remains temporarily supported for draining old pending events, then is retired after reconciliation.

## 12. Automated verification matrix

### 12.1 Artifact/build

- Reproducible setup/update/package archives.
- Every file hash and Ed25519 signature validates.
- Corrupt/extra/path-traversal/oversized ZIP rejected.
- Full-offline setup makes zero network requests.
- Lean setup contacts only pinned official sources.
- Wheel installation uses exact lock and hashes.
- Package has no processing credential or out-of-scope data.

### 12.2 Launcher

Test Windows 10/11 and supported Linux for:

- clean host with no Python;
- Windows Store Python stub only;
- supported and unsupported existing Python;
- online lean setup and disconnected full setup;
- paths containing spaces and non-ASCII characters;
- standard user, UAC accepted/denied, firewall private/public profiles;
- port free, same Station already running, and unrelated port occupant;
- no LAN adapter/multiple adapters/VPN;
- corrupt installer/wheel/file hash;
- interrupted setup and safe rerun;
- second through tenth launch with no internet access;
- colors and ASCII fallback;
- logs contain support codes but no secrets/raw authorization headers.

### 12.3 Package/data lifecycle

- Multiple package versions use one exam database and no new environment.
- Duplicate package import is idempotent.
- New credentials update without duplication.
- Package scope expansion preserves marks/outbox.
- Unsafe config removal/change after entry is blocked.
- Wrong station/exam/package/revoked/unsupported version is quarantined.
- A new exam is routed to a separate database and old exam remains readable.
- Legacy bundle migration preserves counts and deterministic hashes.

### 12.4 Entry/concurrency/recovery

- Complete authoritative mandatory scenarios: no blanks, explicit zero, absent/no marks, attendance first, incident block, total/item mode, two-browser lock race, IndexedDB recovery, process/PC restart, and finalize.
- Test realistic concurrent LAN clients and large station rosters.
- Verify WAL/busy timeout/short transactions.

### 12.5 Sync/security

- Machine credential cannot reach human routes.
- DE cannot reach admin routes or another DE’s scope.
- Admin requires username and password.
- CSRF, session expiry/revocation, rate limiting, and lockout tests.
- Interrupted sync resumes; duplicate event returns original acknowledgement.
- Pending events from older package sync with their original package credential.
- Revoked package yields stable rejection without affecting unrelated packages.
- Portable round trip rejects wrong recipient, alteration, expiry, and replay.
- Reconciliation reaches `MATCHED`; mismatches remain actionable and block closeout.

## 13. Physical acceptance rehearsal

Perform on real clean hardware before go-live:

15. Capture screenshots/logs and obtain Chief IT + system administrator sign-off.

## 14. Definition of done

The Station work is complete only when all of the following are true:

- A non-technical Chief IT can prepare a no-Python computer by double-clicking one setup launcher.
- Full-offline setup works without internet; lean setup clearly requests the offline kit when internet is unavailable.
- Python/environment details are hidden during normal operation.
- No exam package creates an environment or arbitrary SQLite database.
- One station/exam database safely tracks multiple package versions.
- Normal exam packages are small signed ZIP artifacts, not full runtimes or bare JSON.
- The launcher provides polished colored stages, URLs, QR, readable warnings, redacted rotating logs, support codes, and safe failure/rollback.
- Admin authentication is full username + password; DE authentication is initials + PIN; all scope is enforced server-side.
- Central package generation owns the complete Station readiness workflow, including the Offline Station collection channel.
- Direct and portable sync are idempotent, package-authenticated, and reconcilable.
- Backups, restores, upgrades, and old-bundle migration preserve all committed data and pending events.
- Automated suites pass and the physical clean-Windows rehearsal is signed off.
